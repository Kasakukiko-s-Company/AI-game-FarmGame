# ADR-0003：公开 NPC 数据不保存隐藏来源分类

## 状态

已接受

## 背景

Demo 需要十五名村民拥有稳定 ID、姓名、立绘、地图存在和关系数据，同时又必须隐藏五名幸存者与十名重构村民的真实分类。若把 `originType`、`truthKnowledgeLevel` 或 `concealmentStance` 直接写进通用 `characters.json`，内容作者、调试 UI、日志和数据浏览很容易在第一章意外泄底；玩家检查客户端资源时也会看到一个过于直白的答案表。

## 决策

通用角色目录只保存玩家可见或正常运行必需的数据，例如稳定 ID、显示名、本地化键、默认立绘状态和公开关系语境。幸存者/重构村民分类、知情层级、隐瞒动机与后续真相立场只保存在内部叙事文档，以及未来按章节加载的受控叙事数据中。

普通地图生成、日常对白、立绘解析和关系数值不得依赖隐藏来源分类。必须在后续章节使用真相差异时，由叙事事件引用不泄义的稳定事件/角色 ID，而不是让通用 NPC 系统分支检查 `originType`。

这是一条防止偶然泄露和错误耦合的内容边界，不是反数据挖掘保证；本地客户端无法提供绝对保密。

## 后果

### 正面

- 第一章内容、调试日志和通用角色工具不容易意外显示核心真相。
- 日常 NPC、关系和立绘系统不需要理解愿境设定。
- 后续调整某人的真相立场不会破坏地图或普通对白数据。

### 代价

- 内部 NPC Bible 与运行时公共角色数据必须通过稳定 ID 保持同步。
- 真相章节需要单独的数据校验，避免角色 ID 漂移或遗漏。
- 无法阻止有意逆向完整客户端内容，只能减少直白元数据和偶然泄露。

## 被否决的替代方案

### 在 `characters.json` 中增加 `originType`

读取方便，但会把叙事剧透变成所有系统都能访问的普通标签，并鼓励日常代码依赖核心真相。

### 用模糊布尔值或加密字段隐藏

只改变表面名称，仍然把不需要的真相数据装入通用角色目录；自制加密也不能在本地客户端提供可靠保密。

### 每名 NPC 使用不同运行时类型

会让角色行为、关系和地图系统与叙事身份绑定，产生大量重复实现，也违背重构村民与幸存者在日常层拥有同等人格和交互能力的设定。
